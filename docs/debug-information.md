# Debug information

> **Historical m0 design record.** This document describes the archived C23
> reconstruction/MIR pipeline and commands absent from the current pure-Luna
> `main` branch. It is retained as design history, not current implementation or
> CLI documentation. See `architecture.md` and `codebase-backend.md` for current state.

Luna's bootstrap compiler emits source-level debug information without a host
assembler, host linker or target C runtime. The first complete contract covers:

- source files and exact one-based line and column positions;
- source-level function names and code ranges;
- statement rows suitable for breakpoints and source-level single stepping;
- deterministic DWARF 5 in the final static ELF64 executable.

Local-variable locations, type presentation, macro information, unwind tables
and optimized-code location lists are deliberately not fabricated. They require
separate semantic contracts and are outside the unoptimized bootstrap stage.

## Data flow

The pipeline keeps source identity explicit at every boundary:

```text
AST span
  -> typed CFG IR instruction span
  -> x86-64 Machine IR instruction span
  -> .file/.loc in Luna assembly
  -> versioned .luna.debug object section
  -> final-address DWARF 5 generated by lunalink
```

`.file` and `.loc` make emitted assembly reviewable and remain accepted by
LLVM's assembler. Luna's closed object assembler records a location only at the
start offset of the following semantic machine instruction. Synthetic entry,
alignment and function-prologue bytes do not claim a source line.

The relocatable object does not contain partially relocated DWARF. Its
`.luna.debug` section stores code offsets relative to that object's `.text`.
After all input sections have a deterministic final layout, `lunalink` converts
those offsets to absolute addresses and writes standard DWARF. This avoids
debug-section relocation and merge rules in the bootstrap linker.

## Debug IR v1

Debug IR is target-neutral source-to-code metadata. Its public API is declared
in `include/luna/backend/debug/debug_ir.h`. Strings are owned by the Debug IR;
records refer to bounded string offsets rather than process pointers.

The serialized little-endian `.luna.debug` payload is:

| Part | Size | Meaning |
| --- | ---: | --- |
| header | 52 bytes | magic, version, counts, table offsets and total size |
| file record | 8 bytes | path offset and path length |
| location record | 24 bytes | code offset, file id, line, column, flags |
| function record | 40 bytes | half-open code range, source/linkage names, visibility |
| strings | variable | non-NUL path and name bytes |

The v1 magic is `LUNADBG\0` and the version is `1`. File ids are one-based
inside Debug IR. Code ranges are half-open. Locations are strictly increasing,
functions are sorted and non-overlapping, every function must contain at least
one source location, and every location must belong to exactly one function.
Counts, strings, offsets, reserved fields and code ranges are verified both
when the object is produced and when it is consumed.

The object verifier independently decodes `.luna.debug`; corrupting its magic,
layout, strings, locations or code ranges invalidates the object. The linker
accepts at most one project debug section per input object.

## DWARF 5 output

For each input object carrying Debug IR, `lunalink` writes one DWARF 5 compile
unit and one DWARF 5 line table. The executable contains the following
non-allocatable sections:

- `.debug_abbrev`
- `.debug_info`
- `.debug_line`
- `.debug_str`
- `.debug_line_str`

Compile units contain source name, producer, compilation directory, code range
and statement-list reference. Subprogram entries contain the Luna source name,
declaration file/line/column, visibility and exact final code range. The
project-specific language code uses the DWARF user range until Luna receives a
standard language identifier. Linkage names remain available in Debug IR but
are not used as the DWARF primary function name, so ordinary debuggers expose
`main` rather than Luna's encoded ELF symbol.

Line programs use explicit `DW_LNE_set_address` operations after final layout.
Every function is a separate sequence ending at its half-open code end. This
prevents alignment gaps or the next function's prologue from inheriting a
previous source line.

`llvm-dwarfdump --verify` is the conformance oracle in integration tests. When
GDB is installed, the same test also verifies source-line lookup and a
source-name function breakpoint.

## Input and compatibility rules

Project Debug IR is the only debug-information input accepted by the bootstrap
linker. Foreign `.debug_*` and `.zdebug_*` sections are rejected with a precise
diagnostic instead of being silently copied, dropped or partially merged.
Freestanding C23 objects used at the ABI boundary must therefore be compiled
without host debug information.

Debug generation is deterministic and currently always enabled. It changes
neither allocated bytes nor load-segment permissions, and it introduces no
runtime or libc dependency.
